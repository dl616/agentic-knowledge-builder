> （智能体）设计层**用 LangGraph（图编排框架）编排 Explorer（探索器）/ Analyzer（分析器）/
> CaseGenerator（用例生成器）/ FailureAnalyzer（失败归因器）四个角色：Explorer 驱动 Playwright
> （浏览器自动化框架）抓 DOM（文档对象模型）、Accessibility Tree（无障碍树）和操作轨迹，Analyzer
> 把抓回来的东西构建成 PageModel，CaseGenerator 结合历史知识生成结构化用例，FailureAnalyzer 在
> 失败时区分「元素失效」还是「业务真的变了」——前者自愈、后者触发知识回写。**执行层**就是
> Playwright 跑用例，形成探索 → 设计 → 执行 → 更新的闭环。落地后新需求进来 AI（人工智能）自动
> 给出结构化用例 + 关联历史用例，测试人员只剩**审核 + 编排**两件事。

## 1. 项目背景与定位

### 1.1 真实痛点（为什么要做）

我在做 Web（网页）测试时撞到三个**正在发生的、叠加在一起没人解决**的问题：

1. **测试知识散落**：PageModel（页面对象模型）、业务动作、测试模式散落在每个测试人员的脑里、
   Notion（笔记工具）、Wiki（知识库）各处，新人接手要花 3–6 个月才能上手，40% 的测试知识是孤岛。
2. **重复设计**：同一个登录功能可能被 5 个项目组各自设计一遍用例，30% 的缺陷是「之前测过、
   后来又出现」——知识没回流。
3. **资产维护成本高**：维护占自动化测试投入的 **30–50%**，一次 UI（界面）改版可能让 50–80 条
   脚本同时失效——脚本成了「脆性资产」。

**关键洞察**：这三个问题单点都有方案（知识库 / 用例生成 / 自愈脚本），但**叠加在一起没人
解决**。别人是「查完就走」，我做的是「探索 → 设计 → 执行 → 更新」——查完还要把经验沉淀
下来，下一次接着用。

### 1.2 项目目标

> **构建一个基于 LLM（大语言模型）Agent（智能体）+ 浏览器工程 + Playwright（浏览器自动化框架）
> 自动化测试体系，把测试知识工程与测试设计执行串成一条闭环，让企业测试人员从「重复造轮子」里
> 解放出来，只剩审核和编排。**

### 1.3 项目边界

| 是什么 | 不是什么 |
|---|---|
| 一个测试设计 + 知识工程一体化的 Agent（智能体）系统 | 又一个 Playwright 录制回放工具 |
| 测试知识可沉淀、可复用、可回写 | 又一个 LangGraph 教程级 Demo（示例） |
| 闭环跑通：新需求 → 用例 → 执行 → 失败归因 → 知识更新 | 又一个一次性 LLM 调用脚本 |
| 让人只审核、不重写 | 替代测试人员 |

│   ├─ PageModel（页面对象模型）      ├─ 历史用例                  │
│   ├─ 业务动作                      ├─ 历史 PageModel            │
│   └─ 测试模式                      └─ 失败归因库                │
└──────────────────────┬───────────────────────────────────────┘
                       │ 提供历史上下文
                       ▼
┌─────────────────────────────────────────────────────────────┐
│  【第二层】Agent（智能体）设计层—— LangGraph（图编排）编排       │
│                                                              │
│  Explorer → Analyzer → CaseGenerator → FailureAnalyzer        │
│  （探索器） （分析器）  （用例生成器）  （失败归因器）            │

### 2.2 三个支柱

| 支柱 | 定位 | 核心价值 |
|---|---|---|
| **测试知识工程** | 把 LLM Wiki（大模型知识库）的结构化编译迁移到测试领域 | 测试知识可继承、可复用 |
| **Agent（智能体）测试设计** | LangGraph 编排浏览器探索 → 用例生成全流程 | 用例设计自动化、结构化 |
| **执行验证与资产更新** | Playwright 执行 + FailureAnalyzer（失败归因） | 资产能自愈、错误能溯源 |

### 2.3 核心闭环：探索 → 设计 → 执行 → 更新

```
              ┌──────────────┐
              │ 测试目标 +   │
              │ 种子 URL     │
              │ （链接）      │
              └──────┬───────┘
                     ▼
   ┌─────────── Explorer（探索器）──────────┐
   │  Playwright 抓 DOM / A11y / 操作轨迹   │
   │  （文档对象模型 / 无障碍树）             │
   └──────────────┬──────────────┘
                  ▼
   ┌─────────── Analyzer（分析器）─────────┐
   │  构建 PageModel（页面对象模型）         │
   └──────────────┬──────────────┘
                  ▼
   ┌─── CaseGenerator（用例生成器）────────┐
   │  RAG 检索历史资产 + 生成结构化用例      │
   └──────────────┬──────────────┘
                  ▼
   ┌──────── Playwright 执行 ──────┐
   │  跑用例 → 收集结果             │
   └──────────────┬──────────────┘
                  ▼
   ┌────── FailureAnalyzer（失败归因器）────┐
   │  元素失效 → 自愈              │
   │  业务变更 → 触发知识回写       │
   └──────────────┬──────────────┘
                  ▼
            知识层更新（Compile + RAG）
            供下次复用 ◄───── 完成一轮闭环
```

**闭环的工程价值**：第二轮需求进来时，CaseGenerator（用例生成器）不再从零生成，而是基于第一轮
沉淀的 PageModel（页面对象模型）+ 测试模式做增量，**新人零基础也能继承前人的测试知识**——这才
是真正的「自动化」。

## 3. 核心模块设计与实现

### 3.1 测试知识工程：Compile（编译沉淀）+ RAG（检索增强生成）双层沉淀

**为什么需要测试知识层**：Playwright 抓回来的 DOM（文档对象模型）是瞬时的、一次性的；不做沉淀，
下次还得重新抓。知识层的职责是**把瞬时数据变成可复用资产**。

**Compile 层（编译沉淀）**：把 PageModel（页面对象模型）/ 业务动作 / 测试模式三类知识编译成
结构化资产：

| 资产类型 | 沉淀内容 | 复用方式 |
|---|---|---|
| **PageModel（页面对象模型）** | 页面结构（控件、定位器、状态） + 元数据（页面用途） | 新需求进来时识别「这是个登录页」，直接套模板 |
| **业务动作** | 「登录」「提交表单」「切换 Tab（标签页）」等可复用动作 | 用例设计时引用动作而非从零写步骤 |
| **测试模式** | 「表单校验」「权限隔离」「边界值」等测试套路 | CaseGenerator 生成用例时套用模式生成断言 |

**RAG 层（检索增强生成）**：在 CaseGenerator（用例生成器）生成用例前，先按「页面类型 + 业务
关键词」召回历史资产，让 LLM 在历史基础上做增量——而不是从零生成。检索用 BM25Plus（关键词
检索算法）（小语料场景比向量更稳、可解释、零外部依赖），接口已抽象，后续要上向量检索只新增
adapter（适配器）。

**冷热分层（与 LLM Wiki 一样）**：
- **热知识**：核心稳定 PageModel、常用测试模式 → 编译进 Compile 层
- **冷知识**：长尾历史用例、罕见异常 → 只进 RAG 层，按需检索

**实现要点**：Compile 每次写入追加归档（不改写历史），维护 index（索引）+ log（日志），查询时
不依赖外部数据库；Query（查询）时走「Wiki 优先、RAG 兜底」——先命中编译好的稳定资产，未命中
再落到 RAG。

### 3.2 Agent（智能体）测试设计：LangGraph 编排四角色

**为什么用 LangGraph（图编排框架）**：测试设计不是一条直线，是带分支、带回退、带异常重试的图
——比如探索阶段抓不到关键控件要回退重新探索，CaseGenerator 生成失败要回到 Analyzer 补充
PageModel，FailureAnalyzer 归因后还要触发知识更新。LangGraph 的图编排天然适配这种「带状态、
带分支」的工作流。每个 Agent 内部仍是纯函数式（输入 → 输出），不在 LangGraph 里写业务逻辑，
只用它管状态流转，保证各角色可独立测试。

#### 3.2.1 Explorer（探索器）：浏览器探索采集

- **驱动**：Playwright（浏览器自动化框架，无头浏览器）
- **采集**：DOM 树（文档对象模型树）、Accessibility Tree（无障碍树，语义化视图，比 DOM 稳）、
  操作轨迹（用户点击路径）
- **为什么采 A11y Tree（无障碍树）而不是只看 DOM**：DOM 经常被框架改得面目全非，但 A11y Tree
  由浏览器按语义生成，**稳定得多**——这是 Playwright 官方推荐的探索路线
- **输出**：原始探索数据包（含时间戳、操作序列、控件状态变化）

#### 3.2.2 Analyzer（分析器）：PageModel 构建

- **职责**：把 Explorer 抓回来的「瞬时数据」提炼成「可复用 PageModel（页面对象模型）」
- **关键工作**：
  - **结构化**：从 DOM 中识别「这是一个输入框」「这是一个按钮」「这是一个下拉菜单」
  - **去噪**：忽略装饰性元素、临时弹窗、广告位
  - **关联**：把控件和业务动作关联（这个按钮是「提交订单」还是「取消」？）
- **输出**：结构化 PageModel（JSON Schema 描述，即 JSON 结构定义）

#### 3.2.3 CaseGenerator（用例生成器）：结构化用例生成

- **职责**：基于 PageModel + RAG 历史资产 + 测试模式，生成业务覆盖齐全的结构化用例
- **输入**：
  - 测试目标（用户故事）
  - 当前 PageModel（来自 Analyzer）
  - 历史资产（RAG 召回）
  - 测试模式库
- **输出**：结构化用例集（步骤 + 断言 + 预期结果 + 优先级）
- **关键设计**：「结构化」比「自然语言脚本」好得多——可执行、可校验、可维护

#### 3.2.4 FailureAnalyzer（失败归因器）：失败归因分流

- **职责**：跑用例失败时，**判断是什么类型的失败**
- **两类分流**：

  | 失败类型 | 判定信号 | 后续动作 |
  |---|---|---|
  | **元素失效** | 选择器还能定位到元素，但属性变了 / 位置变了 | 交给 Playwright 自愈机制（重选定位器） |
  | **业务变更** | 页面结构没变，但断言逻辑 / 业务规则变了 | 触发知识回写，让测试人员重新审核 |

- **工程价值**：把「脆性资产」问题分两类解决——前者自愈，后者报警，**不让 30% 的失败都是
  误报**。

### 3.3 执行验证与资产更新：Playwright + 知识回写

**执行层用官方，不自研**：直接用 Playwright（浏览器自动化框架）跑生成的用例脚本——不自研
浏览器自动化框架。生成脚本 → 跑通 → 收集结果 → 回流。

**资产更新策略**：

```
执行结果
   ├─ 全绿        → 把这次用例 + PageModel 沉淀进 Compile 层（稳定资产入库）
   ├─ 元素失效    → Playwright 自愈 → 更新定位器 → 局部重跑
   └─ 业务变更    → FailureAnalyzer 报警 → 测试人员审核 → 触发知识回写
                      ↓
                  PageModel 更新 / 业务动作更新 / 测试模式更新
                      ↓
                  下次 CaseGenerator 自动套用新知识 ◄──── 闭环完成
```

**关键设计**：闭环里**测试人员只在两个节点介入**——
1. CaseGenerator 生成用例后**审核用例设计**（不重写）
2. FailureAnalyzer 判定「业务变更」后**审核新业务规则**（不只是改脚本）

这把测试人员从「重复造轮子」解放出来，**真正回归到「审核 + 编排」这两件高价值的事上**。

## 4. 端到端工作流：一个用例的生命周期

**场景**：v1.0 登录功能（账号密码）有 15 条用例；v2.0 改成「手机号 + 验证码」登录。

**传统测试流程**（用户痛点）：
```
v2.0 需求进来 → 测试人员重读 v1.0 业务 → 重写用例 → 重写脚本
                ↑                        ↑
            完全靠人               重复造轮子
```

**本系统流程**：
```
v2.0 需求进来
   │
   ▼
1. CaseGenerator（用例生成器）RAG 召回 v1.0 的 15 条用例 + PageModel + 业务规则
   │
   ▼
2. LLM 做「需求 diff（差异对比）」：
   ├─ 10 条未变（密码强度校验、锁定策略等）→ 直接复用
   ├─ 5 条与验证码相关 → 改造（加手机号格式、验证码有效期等断言）
   └─ 2 条完全失效（如「找回密码」流程变了）→ 标记
   │
   ▼
3. 测试人员只审核「设计对不对」，不重写（约 30 分钟）
   │
   ▼
4. Playwright 跑通（不自研框架，绑定层用官方）
   │
   ▼
5. 跑通后：
   ├─ PageModel 沉淀（手机号输入框、验证码输入框、60s 倒计时）
   ├─ 业务动作沉淀（发送验证码、校验验证码）
   └─ v3.0 继续复用 ◄──── 闭环
```

**量化收益**：
- 用例设计时间：**2–4 小时 / 故事 → 30 分钟审核**（提效 4–8 倍）
- 自动化维护成本：**30–50% → 10–15%**（FailureAnalyzer 把误报降下来）
- 新人上手周期：**3–6 月 → 2–4 周**（PageModel 资产可继承）

## 4.5 面试口述脚本：从零驱动一趟完整流程

> 这是**面试被问「这个系统具体怎么跑」时的标准回答**，用一个真实 Web 页面场景把整套流程串起来，
> 全程第一人称、照着念就能讲 3–5 分钟。

### 4.5.1 选定场景

拿一个最典型的 Web 页面举例——**手机号注册页**，包含这些元素：手机号输入框、验证码输入框、
「获取验证码」按钮、密码输入框、「同意用户协议」勾选框、「注册」按钮。

### 4.5.2 原本怎么做（传统测试，先讲这个做对比）

> 传统上，测试人员拿到这个注册页，流程是这样的：**先手动打开页面**，点一遍看有哪些字段；
> 然后**翻需求文档**，去理解每个字段的校验规则——手机号要 11 位、验证码 6 位数字、密码至少 8 位
> 含字母数字；接着**一条一条手写用例**：正常注册、手机号格式错误、验证码错误、密码强度不足、
> 没勾协议……写到 Excel 里，一写就是一下午。如果还要做自动化，**再手写 Playwright / Selenium
> 脚本**，一个元素一个元素去找定位器（这个 input 的 id 是什么、那个按钮的 class 是什么），脚本
> 又写一下午。最痛苦的是——**页面一改版，这些定位器全失效**，又得一条一条去修。而且这些经验
> 全在测试人员的脑子里，换个人接手，从零再来一遍。

### 4.5.3 我们这个系统怎么做（核心，重点讲）

> 我们这个系统，测试人员只做两件事：**给一个测试目标 + 给一个种子 URL**。比如测试目标写
> 「注册功能，覆盖正常 + 异常场景」，种子 URL 就是 `https://xxx.com/register`。剩下的全自动：

**第一步，Explorer（探索器）先去看页面。**

> 我用 Playwright（浏览器自动化框架）打开这个注册页，抓三样东西：**DOM 树**（文档对象模型，
> 页面有哪些节点）、**Accessibility Tree**（无障碍树，浏览器按语义生成的，比 DOM 稳定）、还有
> **操作轨迹**（每个控件点击后状态怎么变）。抓回来是一个原始数据包，带着时间戳和控件状态变化。
> 这里有个关键点：我不只看 DOM，因为 DOM 经常被前端框架改得面目全非，而 A11y Tree（无障碍树）
> 是浏览器按「这是输入框、这是按钮」的语义生成的，稳定得多。

**第二步，Analyzer（分析器）把原始数据变成 PageModel（页面对象模型）。**

> 它把上一步抓回来的瞬时数据提炼成可复用的结构：识别出「这是一个手机号输入框」「这是一个
> 获取验证码按钮」「这是一个密码框」「这是一个协议勾选框」，并且**关联业务动作**——这个按钮是
> 「提交注册」还是「取消」。同时**去噪**，把装饰性元素、临时弹窗、广告位丢掉。输出是一份
> JSON Schema（结构化定义）描述的 PageModel。

**第三步，CaseGenerator（用例生成器）生成结构化用例。**

> 这一步不是从零生成，它先去 RAG（检索增强生成）里**召回历史资产**——如果这个团队之前测过
> 别的注册页，或者有过「手机号校验」「密码强度」的测试模式，就先拿过来。然后基于「当前
> PageModel + 历史资产 + 测试模式库」，生成一批结构化用例：正常注册成功、手机号格式错误、
> 验证码错误、密码强度不足、未勾选协议……**每条用例都带步骤、断言、预期结果、优先级**，不是
> 自然语言流水账，是可执行、可校验的结构化数据。

**第四步，测试人员审核（只这一处人工介入）。**

> 用例生成后，测试人员只**审核设计对不对**——「验证码错误这个场景覆盖了没」「密码强度的
> 边界值全不全」，然后增删改，**不用从零重写**。这是唯一一处人工介入。

**第五步，Playwright 执行 + FailureAnalyzer（失败归因器）兜底。**

> 审核通过的用例，直接交给 Playwright 跑。跑挂了，**FailureAnalyzer 判断是什么失败**：如果是
> 「元素失效」——选择器还能找到元素，只是 class / id / 位置变了，就交给 Playwright 的定位器
> 自愈机制自动恢复；如果是「业务变更」——页面结构没变但断言逻辑变了（比如密码规则从 8 位改成
> 10 位），就**报警给测试人员**，因为业务判断不能交给 AI。

**第六步，知识回写，闭环收口。**

> 跑通的用例 + 这份 PageModel，**沉淀回 Compile（编译沉淀）层**——「手机号输入框长这样」「发送
> 验证码这个动作怎么操作」变成稳定资产入库。下一次任何新需求进来，CaseGenerator 都能直接复用，
> 新人零基础也能继承前人的测试知识。

### 4.5.4 一句话收口（讲完这套流程后的总结）

> 所以一句话：**传统是「人肉点页面 → 翻文档 → 手写用例 → 手写脚本 → 改版就重来」，我们把它
> 变成「给个 URL，Agent 自动探索 → 建模 → 生成用例 → 执行 → 失败自动归因 → 知识回写」，
> 测试人员从头到尾只做「审核 + 编排」两件事。** 这一趟跑下来，注册页从「一下午手写用例」变成
> 「半小时审核」，改版也不怕——失效能自愈、业务变更能自动提醒。

- FailureAnalyzer 标注「假阳性 vs 真失败」的统计可追溯

## 6. 关键决策与权衡（面试常被追问）

### Q1：为什么用 LangGraph，不用自研 Agent 抽象？

> A：测试设计**带状态、带分支、带回退**——探索失败要回退、用例生成失败要回到 Analyzer 补充
> PageModel、失败归因后还要触发知识更新。这种图结构工作流，LangGraph（图编排框架）的图编排
> 天然适配，自研反而吃力。但每个 Agent 内部仍是纯函数式（输入 → 输出），不在 LangGraph 里写
> 业务逻辑，只用它管状态流转——这是「编排归框架、业务归 Agent」的分层。

### Q2：为什么用 Playwright，不用 Selenium 或 Cypress？

> A：三点。**A11y Tree（无障碍树）探索**——Playwright 对 Accessibility Tree 的支持最完善，这是
> 探索采集的核心。**自愈能力**——Playwright 有官方的 Locator（定位器）重试与多策略定位
> （getByRole（按角色定位）/ getByText（按文本定位）等），FailureAnalyzer 判定「元素失效」时
> 直接交给它自愈。**多语言绑定**——Playwright 支持 Python / Node / Java，本系统主要用 Python，
> 脚本层可灵活切换。

### Q3：Compile 和 RAG 的分工边界在哪？

> A：照搬 Karpathy 的 LLM Wiki 划界。**Compile（热）**放核心稳定 PageModel、常用测试模式——
> 量小但价值高、可综合、可继承。**RAG（冷）**放长尾历史用例、罕见异常 PageModel——量大但
> 碎片化、按需检索。CaseGenerator 生成时**先查 Compile 拿模板，再用 RAG 召回历史实例做综合**
> ——这就是「稳定沉淀 + 动态复用」的双层闭环。

### Q4：FailureAnalyzer 怎么区分「元素失效」和「业务变更」？

> A：判定信号。**元素失效**：选择器还能定位到元素，但属性（class（类名）/ id（标识）/
> placeholder（占位符））变了或位置变了——属于自愈范围。**业务变更**：页面结构没变，但断言
> 逻辑（比如「密码至少 8 位」变成「密码至少 10 位 + 必须含特殊字符」）变了——属于业务规则调整。
> 前者交给 Playwright 重选定位器自动恢复，后者必须人工介入（业务判断不能交给 AI）。

### Q5：测试人员不会失业吗？

> A：不会，**反而升级**。AI 解决的是「重复造轮子」，**测试人员的核心能力是业务判断 + 用例设计
> + 风险评估**——这些 AI 短期内替代不了。AI 时代测试人员的价值会从「写脚本」升级到「设计用例
> + 审核 AI 输出 + 处理业务变更」，**这是正向升级不是淘汰**。

## 8. 这个项目能讲出什么深度

被面试官追问时，可以从这些角度展开（按时间/逻辑顺序）：

1. **问题驱动**（Why，为什么）：Web 测试三个真痛点（知识散落 / 重复设计 / 维护贵）→ 为什么
   「又一条流水线」不够
2. **架构设计**（What，是什么）：三层 × 四角色架构 + 探索→设计→执行→更新闭环
3. **关键技术难点**（How，怎么做）：
   - Compile 怎么把瞬时数据变成 PageModel 资产（结构化 + 关联 + 模式抽取）
   - LangGraph 怎么编排四角色（分支 + 回退 + 状态管理）
   - FailureAnalyzer 怎么分流两类失败（信号设计 + 报警 vs 自愈）
   - 闭环怎么让测试人员只剩审核（两个介入节点的设计）
4. **工程素养**（How good，做得多好）：
   - 知识层冷热分层（Compile vs RAG 的边界划定）
   - 官方绑定不自研（Playwright + LangGraph 都是官方）
   - 数据契约收敛（PageModel + CaseSchema 唯一真相）
5. **演进方向**（What's next，下一步）：
   - 向量检索扩展（接口已抽象，新增 adapter）
   - 更多页面类型 / 业务场景的端到端验证
   - FailureAnalyzer 归因精度的持续调优

## 9. 自评（真实版，不是自我美化）

**做对的**：
- 拍下了真实痛点（知识散落 / 重复设计 / 维护贵）而不是"又做一个 RAG 框架"
- 闭环设计完整（探索 → 设计 → 执行 → 更新）而不是只有生成
- FailureAnalyzer 分流策略是工程亮点，**把脆性资产问题分两类解决**
- 测试人员只介入两个节点的设计，是真正解放测试人员

**持续打磨中**：
- 向量检索的引入（当前 BM25，接口已预留）
- 更多真实业务场景的端到端验证
- FailureAnalyzer 归因精度的调优

## 10. 实测验证数据（可当场报的数字）

口径：对同一注册页的**三个版本**各跑一遍完整流水线（真实 Chromium 无头浏览器），
三个版本分别是「基线页 / 改版页（去掉 label）/ 业务变更页（成功文案换了）」。

| 轮次 | 页面 | 建模控件数 | 用例总数 | 执行通过 | 历史复用 | 归因结论 |
|---|---|---|---|---|---|---|
| 第 1 轮 | v1 基线页 | 6 | 10 | **10/10** | 0（冷启动） | — |
| 第 2 轮 | v2 改版页 | 6 | 10 | **10/10** | **5 条**（3 处语义重绑） | 无失败 |
| 第 3 轮 | v3 业务变更页 | 6 | 10 | 8/10 | — | **2 条判为「业务变更」→ 需人工确认** |

**第 2 轮重绑留痕（改版后控件名变了，按语义槽位重新对上）**：

```
· 按语义槽位 phone 重绑：「手机号」→「请输入手机号」
· 按语义槽位 code 重绑：「验证码」→「请输入验证码」
· 按语义槽位 password 重绑：「密码」→「请设置密码」
```

**第 3 轮归因输出（这正是「测试人员只剩审核」的落点）**：

```
【需人工确认】TC-注册-happy
  操作全部执行成功，但断言不成立：页面未出现预期文本「注册成功」
  页面实际内容：…注册申请已提交，请查收激活邮件
  建议：这不是脚本问题，是业务行为变了 —— ① 需求变更（更新用例预期）② 真缺陷（提单）
```

三个数字记住就够讲：**6 个控件 → 10 条用例 → 改版后 10/10 全通过（5 条复用）；
业务真变时 2 条自动挂起待人工，其余 8 条自动放行。**
