# 项目规划 — 多 Agent 知识构建平台

> **Agentic Knowledge Builder**：一个多 Agent 协作、查存混合的企业级知识库构建与问答平台。

| 项 | 内容 |
|---|---|
| 文档版本 | v2.0（定稿） |
| 日期 | 2026-08-21 |
| 状态 | 定稿 |

---

## 1. 一句话定位

> **丢一堆杂乱文档进来，一个总控 Agent 调度五个专项 Agent 分工协作，自动构建出一个「能查、能问、答案有出处、知识越用越厚」的企业级知识库。**

---

## 2. 背景与洞察

### 2.1 三个被验证的趋势

1. **摄取是 RAG 的真正瓶颈**：多个来源一致强调「摄取质量决定检索上限」「垃圾进垃圾出」。模型再好，喂进去的文档是坏的，答案就是错的。
2. **纯检索（RAG）不沉淀**：RAG 是「外卖员」——每次查询从零检索，知识不积累、无法跨文档综合。
3. **纯编译（LLM-Wiki）不规模化**：Karpathy 本人划界——LLM Wiki 只适合「个人 + 100~200 篇稳定语料」，量大了必须回到检索层。

### 2.2 我们的判断

**单点已经卷不过**（摄取有 Unstructured/Docling/MinerU，检索有成熟的向量库）。**但「把这两者 + 多 Agent 编排整合成一个企业级知识构建平台」的完整方案，是空白的。**

---

## 3. 三大核心设计

| 支柱 | 定位 | 说明 |
|---|---|---|
| **多 Agent 编排**（核心） | 项目灵魂 | 用 LangGraph 编排一个 6 角色 Agent 团队，把知识库构建过程协作化、自动化 |
| **摄取保真**（特色） | 团队里的「尖刀连」 | 识别+解析+清洗，代码缩进/表格/公式/符号不丢，是所有下游的地基 |
| **三层混合知识架构**（查存） | 企业级关键 | Compile 层编译沉淀 + RAG 层实时检索 + Memory 层用户记忆，取长补短 |

---

## 4. 多 Agent 团队（核心）

| Agent | 职责 | 技术 |
|---|---|---|
| **Orchestrator 总控** | 识别类型、规划流程、调度协调 | LangGraph 编排 |
| **Ingest 摄取**（特色） | 分类、解析、清洗、录入保真 | Docling/MinerU + 自研保真 |
| **Quality 质检** | 校验丢字/乱码/残缺，触发纠错重试 | 规则 + LLM 校验 |
| **Index 索引** | 分块 + 向量化 + 写入 | Qdrant + 嵌入模型 |
| **Retrieval 检索** | 混合检索 + 重排 | BM25 + 向量 + reranker |
| **Answer 问答** | 带引用生成答案 | LLM + 引用标注 |

**协同模式**：Orchestrator-Worker（总控调度 + 专项执行），通过统一契约通信，每个 Agent 可独立测试、可插拔扩展。

---

## 5. 三层混合知识架构（查存互补）

### 5.1 三层分工

| 层 | 管什么 | 时机 | 一句话 |
|---|---|---|---|
| **Compile 层**（LLM-Wiki） | 核心稳定知识：概念/框架/规范/政策 | 摄取时编译 | 「我们确定知道的东西」 |
| **RAG 层**（向量库） | 长尾海量文档：历史记录/论文/会话 | 查询时检索 | 「语料里现在有什么」 |
| **Memory 层**（记忆） | 用户偏好/过往会话 | 会话时写 | 「这个用户是谁」 |

### 5.2 三种互补机制（定稿用全套）

1. **冷热分层**：核心/高频文档 → 编译进 Wiki（热）；长尾/低频 → 只进向量库（冷）。
2. **Wiki 优先、RAG 兜底**：先查 Wiki，不够 → 落到 RAG 深挖。
3. **编译回流（re-absorption）**：RAG 里被频繁命中、证明有价值的片段 → 后台异步编译进 Wiki，「从冷变热」。

### 5.3 这解决了什么

- **量大了怎么办** → 冷热分层：不全编译，核心进 Wiki、长尾走向量库。
- **怎么取长补短** → Wiki 负责「质量+综合」，RAG 负责「全量+精确」，回流持续互相喂养。
- **企业场景** → Wiki=团队共识知识，RAG=海量原始资产，Memory=个性化上下文。

## 6. 技术栈（主流）

| 层 | 选型 | 理由 |
|---|---|---|
| 编排 | LangGraph | 多 Agent 事实标准，checkpoint/human-in-the-loop |
| 摄取 | Docling / MinerU / PyMuPDF | 主流解析器，混合架构用传统解析器做主力 |
| 向量库 | Qdrant | 专业级、原生混合检索、丰富过滤 |
| 检索 | BM25 + 向量 + reranker | 混合检索已是 2026 标配 |
| 持久知识 | Markdown Wiki（LLM-Wiki 契约） | 开放、可 git、可审计 |
| 模型 | 可插拔 Adapter（Ollama/DeepSeek/OpenAI） | 模型无关 |
| 后端 | FastAPI | 异步、自动文档、主流 |
| 测试/评测 | pytest + RAGAs + 自建评测集 | 「指标说话」 |

## 7. 里程碑路线

沿用「逐步摸透」的共建节奏，每阶段产出可运行、可验证的成果：

| 阶段 | 内容 | 交付物 | 验证 |
|---|---|---|---|
| M0 | 骨架 + 数据结构 + 识别器 | Document/Chunk + Scanner | 单元测试 |
| M1 | 摄取 Agent（PDF/网页/图片） | ingest 模块 | 已知样本保真率 |
| M2 | 质检 Agent | quality 模块 | 丢字/乱码检出率 |
| M3 | 索引 + 混合检索 | index/retrieve | 检索命中率 |
| M4 | 问答 Agent（带引用） | answer 模块 | RAGAs |
| M5 | Compile 层（LLM-Wiki 沉淀） | wiki 模块 | index/log 一致性 |
| M6 | 三层路由 + 编译回流 | router + re-absorption | 端到端 |
| M7 | Memory 层 + 企业接入 + UI | memory + connectors | 企业验收 |

### 7.1 最小可演示子集（优先交付）

完整 M0-M7 周期长，先抽一个「最小可演示子集」尽早交付可演示版本：

> **M0 + M1 + M4 + M5** → 一个「丢文档进去 → 能问 → 答案有出处 → 沉淀成 Wiki」的可演示 demo。

其余（质检精细化、三层路由、企业接入）作为「深化」迭代，不影响主 demo 交付。

## 8. 评测与测试（体现基础工程能力）

- **单元测试**：每个 Agent 独立可测（pytest），mock LLM/向量库。
- **自建评测集**：已知内容的「脏样本集」，断言保真率、命中率、忠实度。
- **RAGAs**：检索质量 + 生成质量「指标说话」。
- **CI**：代码规范、类型注解、覆盖率门槛。

### 8.1 验证计划（横向对比，回答「凭什么比竞品强」）

差异化不能只靠叙事，必须用可测量的数字说话：

1. **横向保真率对比**：在同一批「已知内容脏样本」（含代码缩进/表格/公式/扫描件）上，跑我们 + Docling + MinerU + Unstructured，逐项对比代码缩进还原率、表格还原率、符号保留率。
2. **检索质量对比**：同一语料上，对比三层混合检索 vs 纯 RAG 的命中率、上下文精确率（RAGAs context precision/recall）。
3. **成本量级记录**：记录每阶段 LLM 调用次数与 token 消耗，给出「每 1000 页摄取成本」量级。

只有这三个数字出来，「差异化」才从说辞变成证据。

## 9. 竞品与差异化

| 竞品 | 现状 | 我们的差异化 |
|---|---|---|
| Unstructured/Docling/MinerU | 单一解析管线，成熟 | 摄取只是我们一个 Agent，且主打保真 |
| 传统 RAG | 只查不存、不沉淀 | 我们有 Compile 层沉淀 + 回流 |
| LLM-Wiki（纯） | 只适合个人小语料 | 我们三层混合，企业可规模化 |
| AWS IDP Accelerator | 偏企业合规、重 | 我们通用、可全盘掌握 |

**差异化一句话**：别人做「一条流水线」或「单层检索」，我们做「**一个会分工、会质检、会沉淀、查存互补的 Agent 团队**」。

---

## 10. 成本与安全（企业级的两个硬约束）

**成本模型**：多 Agent 编排 + LLM 编译会放大 token 消耗，需按量级规划：

| 环节 | 是否调 LLM | 成本控制 |
|---|---|---|
| 摄取解析 | 否（传统解析器） | 近乎免费 |
| 摄取分类/路由 | 是（轻量判断） | 用便宜模型，只对「不确定」的样本调用 |
| 质检 | 是（校验） | 规则先行，LLM 只复核疑似异常 |
| Compile 编译 | 是（核心） | 冷热分层，只编译核心文档 |
| 问答生成 | 是 | 按需，一次查询一次调用 |

**安全/权限**（当前阶段预留设计，不实现）：企业知识库必须支持「文档级访问控制」——不同角色只能检索被授权的知识。三层架构天然支持：Memory 层按用户隔离，Compile/RAG 层按文档 ACL 过滤。**首版先做单用户，但契约里预留 `acl` 字段。**

---

## 11. 风险与对策

| 风险 | 对策 |
|---|---|
| 多 Agent 复杂度 | 先搭 Orchestrator 骨架，Agent 逐个点亮，不过度设计 |
| 摄取保真难度 | 借鉴 Docling/MinerU 做主力，自研保真做增量，评测驱动 |
| 编译成本（LLM-Wiki） | 冷热分层，只编译核心，长尾走向量库 |
| 范围蔓延 | 严格 M0→M7 递进，每阶段有明确完成判据 |

---

## 12. 一句话总结

> **核心是用多 Agent 编排，把一个企业知识库的「构建 + 查询 + 沉淀」全流程自动化、协作化；摄取保真是团队里最锋利的一把刀，三层混合架构（Compile + RAG + Memory）是它区别于「又一个 RAG demo」的骨架。**
