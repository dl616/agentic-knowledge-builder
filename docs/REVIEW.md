## 结论先行

**立意方向是站得住的，但项目目前处于「规划走得很快、落地跟不上」的状态**——三份核心文档（README/PRD/DEVELOPMENT）彼此不一致，一半是历史遗留、一半是规划超前于代码。这是**最需要立刻处理的问题**，否则继续往下写代码只会加剧混乱。

## 一、致命问题（必须先处理，否则继续开发会越乱）

### 1.1 README 与 PRD 相互矛盾 🔴

- `README.md`（早期版本）：**"这个项目不追求多 Agent 花活，不堆企业级重装"**
- `docs/PRD.md`（v2.0 定稿）：**核心卖点就是"多 Agent 编排 + 企业级三层知识架构"**

这是两个不同阶段留下的矛盾表述，**README 完全没跟上定位演进**。如果现在有人（面试官）先看 README，会得到跟 PRD 完全相反的第一印象。

**必须做**：立刻重写 README，与 PRD v2.0 对齐。

### 1.2 `akb-dev` skill 内部自相矛盾 🔴

同一份 skill 文件里：
- 「核心架构」章节：**6 个 Agent 是定稿架构**
- 「关键约定」+「Pitfalls」章节：**"不铺多 Agent 花活""过度设计（多 Agent 花活）是要避免的坑"**

这是我在项目立意"规模克制"阶段写的措辞，收敛到"多 Agent 是核心卖点"之后没有同步修正，**AI 下次加载这个 skill 会拿到自相矛盾的指令**。

**必须做**：修正 skill，明确界限——"多 Agent 编排"本身不是要克制的花活（它是核心），要克制的是"过早引入五种外壳、上下游全铺开、Agent 数量无限细分"。

### 1.3 规划目录 ≠ 实际目录 🔴

`DEVELOPMENT.md` 规划的目录结构（`agents/`、`knowledge/`、`adapters/`、`schemas.py`）**一个都不存在**。实际代码还停留在更早期的结构：

```
DEVELOPMENT.md 规划          实际存在
─────────────────────────────────────────
pke/agents/orchestrator.py   ❌ 不存在
pke/agents/ingest/pdf.py     实际在 pke/ingest/pdf.py（旧结构）
pke/knowledge/compile.py     ❌ 不存在
pke/schemas.py               实际是 pke/ingest/base.py（旧结构，命名也不同）
pke/chunk/ pke/index/        ⚠️ 空壳目录，是更早期方案(RAG单管线)的遗留，
pke/query/ pke/store/           已被新架构取代，但没清理，容易误导
```

**这不是小问题**——如果现在直接照 DEVELOPMENT.md 写新代码，会跟现有代码结构冲突或重复。

**必须做**：先做一次目录迁移/清理，让代码结构对齐 DEVELOPMENT.md，再继续写新功能。

## 二、工程规范"写了但没落地" 🟡

| DEVELOPMENT.md 规定 | 实际情况 |
|---|---|
| uv + `pyproject.toml` 管理依赖 | 只有 `requirements.txt`，且是纯手写、非锁定版本 |
| Git 规范（Conventional Commits/分支） | **项目根本没有初始化 git 仓库**（`fatal: not a git repository`），规范无从落地 |
| pytest 85% 覆盖率 + 三层测试目录 | `tests/` 下只有一个空的 `__init__.py`，**零测试** |
| CI（ruff+mypy+pytest 三绿） | 没有 `.github/workflows/`，**CI 不存在** |
| mypy --strict | 现有代码类型注解不够严格（如 `scanner.py` 的 `ScanResult.features: dict` 是裸 `dict`，不是 `dict[str, Any]`），直接跑 `mypy --strict` 会报错 |

**判断**：这不代表规范写错了，代表**规范是"目标状态"，但项目还没有一次"补齐工程地基"的动作**。继续裸写功能代码，地基缺口只会越滚越大。

## 三、立意与竞品差异化——理论成立，但缺验证计划 🟡

PRD 的差异化叙事（多 Agent 编排 + 摄取保真 + 三层混合知识）逻辑自洽，但有三处是"叙事正确"而非"验证过"：

1. **每个差异化点，单独看都有更强的现成对手**：
   - 多 Agent 编排 → LangGraph 官方案例本身就有
   - 摄取保真 → Docling/MinerU 已经做得很深
   - 三层混合知识 → Zep（时序知识图谱）比自建 Compile 层更成熟

   **你的护城河是"三者组合"，但 PRD 里没有回答"为什么组合比单点更强"的具体机制**，目前更像是并列陈述而非论证。

2. **"三层混合"的规模假设未量化**：PRD 引用 Karpathy「个人 100-200 篇」的边界，但企业场景"核心稳定知识"子集到底是多大（500 篇？5000 篇？），**没有给出量化假设**，也没有压力测试计划。这会导致"冷热分层"的阈值全靠拍脑袋。

3. **没有对比评测计划**：既然对标 Unstructured/Docling，PRD 却没写"在同一批测试文档上，我们和它们分别跑一遍、对比保真率"这样的验证动作。没有这个，差异化只是说辞，答不出"你比它们强在哪个可测量的数字上"。

**建议**：PRD 补一节「验证计划」——至少包含（a）与 1-2 个开源工具的横向保真率对比、（b）冷热分层阈值的量化假设。

## 四、缺失的非功能性需求 🟡

面向"企业级"定位，PRD 里没有覆盖：

- **数据安全/权限**：企业知识库必须有访问控制，PRD 只在"竞品调研"里提到别人的 governance，自己的方案没设计。
- **成本模型**：Quality Agent、Compile 层编译都要调 LLM，多 Agent 编排会显著放大 token 消耗。目前没有任何成本量级估算——面试官很可能会问"这套东西跑起来一天要花多少钱"。

**建议**：至少加一段「成本与安全的初步设计」，哪怕是"当前阶段暂不实现，但设计已预留扩展点"这种诚实表述。

---

## 五、里程碑节奏偏长，缺"最小可演示子集" 🟡

M0→M7 七个阶段，是完整路线，但如果目标包含"面试官/leader 看了有想法"，**这个节奏交付第一个可演示版本太慢**。

**建议**：从 M0-M7 里抽一个"最小可演示子集"单独标出来，例如：

> `M0(骨架) + M1(摄取Agent) + M4(问答Agent，跳过复杂检索) + M5(Wiki沉淀)` → 一个「丢文档进去、能问、有出处」的**可演示 demo**，其余（质检 Agent 的精细化、三层路由、企业接入）作为"深化"迭代。

这样两周左右就有东西可以演示，而不是等一整条路线走完。

## 六、做得对的地方（不能只挑错）

- **摄取保真的方法论是扎实的**：等宽字体检测代码块、扫描件阈值检测，是真正复现并解决了 K4/K5 坑，不是空谈。
- **"已知样本断言"验证法**贯穿始终，这是靠谱的工程方法，比"感觉还行"强得多。
- **三层知识架构的引用有据**（Karpathy 边界、腾讯落地案例），不是拍脑袋编的。
- **多轮收敛的过程本身就是好故事**：从"个人知识库"→"知识层"→"知识ETL"→"多Agent摄取"→"多Agent知识构建平台"，每一步都有具体质疑推动收敛——这个过程比任何单一结论都更能体现你的技术判断力，**建议把这段收敛过程也写进 README 或面试叙事里**，它本身就是"批判性思维"的证据。
