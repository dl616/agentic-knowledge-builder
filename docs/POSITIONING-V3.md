# 项目定位 v3：测试用例与测试知识的一体化生命周期管理

> 本文是对 `STRATEGY.md` §二「项目定位」的第三次校准，回答一个新问题：
> **不做脚本生成、改做用例生成，到底有没有真实的业务价值？价值在哪一环？**
> 结论均基于对全网真实测试痛点的调研（含腾讯云、InfoQ TID、51Testing、阿里云等）与对 AKB 现有代码的核实。
> 日期：2026-08-27

---

## 0. 一句话结论

不做「脚本生成器」（Playwright 官方 v1.56+ 已内置 Planner/Generator/Healer，免费吃掉），
也不做「裸用例生成器」（需求→用例的 LangGraph 流水线已是博客级方案，赛道拥挤）。

**做「带记忆的测试用例闭环」**：需求/版本更新进来时，带着历史测试资产生成用例，
**人工只审核、不重写**，跑通后把结果沉淀回资产，下次版本更新直接复用。

护城河不在「生成」，而在「生成时带着历史、跑完后沉淀回历史」的**积累复用闭环**——
而这恰恰是 AKB 已经练成的能力（摄取保真 + Compile 结构化沉淀 + RAG 检索 + Router 冷热分层）的自然迁移。

## 1. 调研结论：真实痛点（量化）

### 1.1 用例设计是流程瓶颈

| 痛点 | 数据 | 来源 |
|---|---|---|
| 单个用户故事用例设计耗时 | 平均 2–4 小时 | m.zpedu.com 敏捷测试趋势 |
| AI 生成用例提效 | 60 秒产出 20+ 条，效率提升 3–5 倍 | ima.qq.com LangGraph 实战 / Roost.ai |
| AI 能多找边界值/异常场景 | 比人工多 30–40% | aitestingguide.com |
| AI 幻觉率（需人工审核） | 8–15%，用评测工具可压到 <3% | aitestingguide.com |

### 1.2 自动化维护是最大隐性成本（比写用例更痛）

| 痛点 | 数据 | 来源 |
|---|---|---|
| 维护占自动化总投入 | 30–50%，部分团队 >50% | shiftasia.com |
| 维护占自动化周期 | 40–60% | m.zpedu.com |
| 一次 UI 变更失效脚本数 | 50–80 条 | cloud.tencent.com 智能体测试踩坑 |
| 自愈定位器降低维护 | 减少 80% | m.zpedu.com |

### 1.3 知识无法沉淀是「组织级」痛点（AI 最难替代、护城河最深）

| 痛点 | 数据 | 来源 |
|---|---|---|
| 新人独立上手周期 | 3–6 个月 | javaguidepro.com |
| 关键知识存在个人脑子里 | 40% 知识孤岛 | javaguidepro.com |
| 重复缺陷占比 | 约 30% 同类缺陷反复出现 | javaguidepro.com |
| 结构化知识库压缩上手 | 14–21 天 → 72 小时 | CSDN 知识库实践 |
| 知识库检索准确率提升 | 52% → 89%（向量+语义） | CSDN 知识库实践 |

### 1.4 关键信号：企业落地 AI 测试的三大难题，正好撞上 AKB 的能力

阿里云开发者社区把「AI 生成用例难落地」归结为三件事：

1. **工具碎片化**（ChatGPT + 知识库 + Prompt + Excel 割裂）
2. **图文混合需求**（只有文本会丢信息）
3. **测试资产管理**（生成之后：用例版本管理、需求关联、脚本关联，否则资产越来越乱）

第 3 条是「生成」之后的真问题，也是大多数「生成器」产品故意不碰的脏活——
**它正是 AKB 的 Compile（结构化沉淀）+ Router（冷热分层）+ RAG（关联检索）要解决的。**

## 2. 还原真实场景（你要解决的正是这个）

你描述的场景，本质是「**测试资产的生命周期**」，一个版本演进的循环：

```
v1.0：需求 → 手动写 15 条「登录」用例 → 手动跑通 → 再写自动化
        ↑ 痛点1：写用例慢        ↑ 痛点2：写脚本+维护贵
        ↓
       （15 条用例 + 登录 PageModel + 业务规则，全部散落在文档/表格/脚本里，没沉淀）
        ↓
v2.0：「登录」改成「手机号+验证码」登录
        ↑ 痛点3：重新理解 v1 的业务、重写用例、旧脚本全废
```

AI 化之后的目标闭环：

```
v2.0 需求文档丢进来
  → RAG 检索到 v1.0 的 15 条登录用例 + PageModel + 业务规则
  → LLM 对比需求差异，生成 v2.0 用例：
       复用未变的 10 条 / 新增验证码相关 8 条 / 标记失效 2 条
  → 人工审核（只审核「设计对不对」，不重写）
  → 自动化执行跑通（Playwright 官方，不自研框架）
  → 跑通后：新用例 + 新 PageModel 沉淀回知识库
v3.0 再更新 → 继续复用，越用越厚、越用越准
```

这就是「积累复用」的具体机制：**Compile 负责沉淀，RAG 负责复用，Router 负责分层（登录是核心高频资产，升级为 hot，永远优先召回）。**

---

## 3. 差异化：为什么不是「又一个用例生成器」

| 技术路线 | 做法 | 致命短板 |
|---|---|---|
| Prompt 生成 | 需求 → LLM → 用例 | 不稳定、无历史、无规范 |
| RAG 生成 | 需求 + 历史用例检索 → LLM | 只读历史，**跑完不沉淀**，知识不增长 |
| Agent 生成 | 多 Agent 流水线生成 | 生成能力强，但**资产管理仍是空白** |
| **AKB（本方案）** | RAG 生成 + 执行 + **失败归因 → 资产回流** | 生成只是入口，闭环才是本体 |

核心差异一句话：**别人是「查完就走」，AKB 是「查完、跑完、沉淀完再走」——知识会越用越厚。**

## 4. 映射到 AKB 现有代码（复用 vs 新增）

### 4.1 直接复用（已跑通的代码）

| AKB 模块 | 迁移到测试领域的角色 |
|---|---|
| `pke/agents/ingest/{pdf,text,web}.py` | 吃 PRD/需求文档/原型说明/历史用例 |
| `pke/scanner.py` | 识别输入类型（需求 vs 用例 vs 页面） |
| `pke/schemas.py` | `Document/Chunk` → `需求/用例` 的数据契约 |
| `pke/knowledge/rag.py`（BM25Plus） | 检索历史相似用例、相似 PageModel |
| `pke/knowledge/compile.py`（WikiStore） | 把用例编译成 PageModel/业务规则/测试模式的**结构化资产** |
| `pke/knowledge/router.py` | 冷热分层：高频核心用例（如登录）升级为 hot 资产 |
| `pke/agents/orchestrator.py` | 编排「生成→审核→执行→沉淀」闭环 |
| `pke/agents/quality.py` | 用例质检：去重 / 冲突 / 遗漏核心场景 |

### 4.2 需新增（本方向独有的部分）

| 新增模块 | 职责 |
|---|---|
| `CaseSchema`（用例契约） | 用例 ID / 模块 / 前置条件 / 步骤 / 预期 / 优先级 / 类型 / 关联需求 |
| `CaseGenerator`（生成 Agent） | RAG-generation：历史资产 + 新需求 → 用例，含需求 diff 复用/新增/失效标记 |
| 执行绑定层 | 用例 ↔ Playwright/Pytest 可执行脚本的映射（**不自研框架，绑定用官方**） |
| `FailureAnalyzer`（归因 Agent） | 失败归因：区分「选择器失效（丢给官方 Healer）」vs「业务真的变了（报警给人，触发资产更新）」 |
| 资产回流 | 跑通后把用例 + PageModel 沉淀回 WikiStore，形成闭环 |

## 5. 目标架构（闭环）

```
            新需求 / 版本更新
                  │
                  ▼
        ┌─────────────────────┐
        │     Orchestrator    │  总控：识别意图 → 调度闭环
        └─────────┬───────────┘
                  │
   ┌──────────────┼───────────────────┐
   ▼              ▼                   ▼
[摄取]         [检索历史]           [生成]
需求文档    RAG 召回历史用例      CaseGenerator
PDF/原型    + PageModel         (RAG-generation)
   │              │                   │
   │              └──────┬────────────┘
   │                     ▼
   │              人工审核（human-in-the-loop）
   │              只审「设计对不对」，不重写
   │                     │
   │                     ▼
   │             自动化执行（Playwright/Pytest）
   │                     │
   │            ┌────────┴─────────┐
   │            ▼                  ▼
   │        跑通 ✅            失败 ❌ → FailureAnalyzer
   │            │                  │
   └────────────┼──────────┐       ├─ 选择器失效 → 丢给官方 Healer
                ▼          │       └─ 业务变更 → 报警给人
        Compile 沉淀 ◄──────┴───────┘      （触发资产更新）
        用例/PageModel/规则
        写入 WikiStore（cold→hot）
                │
                └────────► 下次版本更新复用（回到「检索历史」）
```

## 6. 分阶段落地（按「这一步能不能独立验证价值」排序）

| 阶段 | 内容 | 前置依赖 |
|---|---|---|
| **S1 最小闭环（Demo）** | 登录功能 v1→v2：摄取需求 → 检索历史用例 → 生成 → 人工审核 → 沉淀。用「登录加验证码」跑通端到端 | 仅需 LLM 接入 |
| S2 执行绑定 | 用例映射到 Playwright 脚本，跑通 + 结果回填 | S1 |
| S3 失败归因 | FailureAnalyzer 区分选择器失效 vs 业务变更 | S2 |
| S4 资产回流 | 跑通后自动沉淀、Router 冷热升级 | S3 |
| S5 向量检索 | embedding + 混合检索，语义召回「登录慢 ≈ 认证响应延迟」 | LLM/本地 embedding |

> S1 就是「可验证的锚点场景」：一个最小但完整的闭环，能用来面试演示、也能验证架构是否成立。

## 7. 阻塞与决策（同 STRATEGY.md，未变）

1. **LLM 接入是硬阻塞**：S1 的「生成」、Compile 的「真编译」都依赖它。
   - DeepSeek/OpenAI API key（成本低、需联网、数据出本机）
   - 本地 Ollama（免费、数据不出本机、能力弱于云端）
2. **未提交的三个文件**（orchestrator/quality/router，42 测试绿）——是否保留并提交，决定 S 阶段的代码基线。
3. **验证锚点**：本方案锁定「登录功能版本演进」作为 S1 的最小验证场景，不再三选一。
