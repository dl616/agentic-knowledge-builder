## 一、项目现状（如实核实，非 PRD 转述）

### 1.1 现有代码结构

```
pke/
├── schemas.py              Document / Chunk 数据契约
├── scanner.py               文件类型识别（PDF/文本/网页/Markdown）
├── config.py                集中配置（阈值、路径）
├── agents/
│   ├── base.py               Agent 抽象基类 + AgentMessage 契约
│   ├── ingest/                摄取：pdf.py / text.py / web.py
│   ├── index.py               索引 Agent（写入 RAG）
│   ├── retrieval.py           检索 Agent（BM25 召回）
│   ├── answer.py              问答 Agent（带引用组装，不调 LLM）
│   ├── compile.py             编译 Agent（Document→Markdown，不调 LLM）
│   ├── quality.py            [新增未提交] 质检 Agent
│   └── orchestrator.py       [新增未提交] 总控 Agent
└── knowledge/
    ├── rag.py                 RAG 层：BM25Plus 检索 + 带引用组装
    ├── compile.py              Compile 层：WikiStore（目录结构+归档+index+log+lint）
    └── router.py              [新增未提交] 冷热分层 + 查询路由
```

**测试现状**：42 个测试全部通过（unit 33 + integration 9），ruff/mypy 全绿，CI 已配置。

### 1.2 诚实的能力边界

| 模块 | PRD 描述 | 代码实际做到的 | 差距 |
|---|---|---|---|
| 摄取 | "识别+解析+清洗保真" | PDF代码块保真（等宽字体识别）、网页去噪（trafilatura）、Markdown结构化分块 —— **这部分名副其实** | 无图片OCR、无表格深度结构化 |
| 索引/检索 | "混合检索" | 仅 BM25Plus 关键词检索，**无向量检索** | 无 embedding，语义相似度查询查不到 |
| 问答 | "带引用生成" | 只是把召回片段拼接标号 `[1][2]`，**不调 LLM，没有真正的"生成"** | 本质是检索结果格式化，不是问答 |
| Compile层 | "LLM-Wiki编译沉淀" | 只是 Document→Markdown 的格式转换，**没有LLM参与，entities/concepts目录一直是空的** | 没有实体抽取、没有语义建链、没有矛盾检测 |
| 三层架构 | "Compile+RAG+Memory协同" | Memory层**完全不存在**；Compile和RAG互不通信（今日刚补的router.py是第一次让它们对话） | Memory是空白 |
| 多Agent编排 | "Orchestrator调度6个Agent" | Orchestrator今日刚写（未提交），此前**完全不存在**，四个Agent此前是孤立脚本 | 编排刚起步 |

**核心结论**：AKB 目前是"**摄取保真做得扎实的单点能力 + 一套尚未跑通的知识架构骨架**"。摄取这一块的技术含量是真的（等宽字体识别代码块、BM25Plus修复小语料IDF退化，这些是可以在面试上展开讲的真坑），但"多Agent协作"和"三层知识架构"目前更接近"设计稿"而非"运行系统"。

### 1.3 待评估：今日新增但未提交的三个文件

`orchestrator.py`（总控调度）、`quality.py`（质检）、`router.py`（冷热分层+查询路由）——这三个文件把"质检→路由→索引→按条件编译"这条链路真正跑通了（42个测试里有17个是验证这条链路），是当前离PRD承诺最近的一次实质进展。**是否保留由你决定**，本文档后续架构描述里，会分别标注"若保留"和"若不保留"两种情况下的现状基线。

## 二、项目定位（重新校准）

### 2.1 旧定位的问题

PRD v2.0 的定位——"丢一堆杂乱文档进来，总控Agent调度五个专项Agent，构建能查能问答案有出处知识越用越厚的企业级知识库"——**问题不是错，是空**。它没有回答一个关键问题：

> **这个系统嵌入了知识工作者的哪一个真实工作环节？**

现在的风险是：AKB 看起来是"一个知识库管理系统的技术演示"，服务对象是抽象的"企业"，没有一个具体场景在验证它。

### 2.2 新定位

> **AKB 不是"知识库 Demo"，是"知识资产的生命周期管理系统"——解决的是知识工作中"内容一次进来就没人管"的真实痛点：进来的东西该不该被信任、该沉淀还是该丢、沉淀后过时了怎么发现。**

对应到可验证的三个真实场景（任选一个作为验证场景，不要三个同时做）：

| 场景 | 具体问题 | AKB 对应能力 |
|---|---|---|
| 个人技术笔记库 | 一堆技术文档/博客收藏，多了之后找不到、记不住 | 摄取保真 + Wiki优先/RAG兜底检索 |
| 团队知识沉淀 | 团队文档散落在飞书/Wiki/聊天记录，新人不知道历史决策 | 冷热分层（决定哪些沉淀成"团队共识"）+ 矛盾检测 |
| 客服知识库 | FAQ文档更新后旧答案还在被引用 | Quality Agent + lint 检测知识失效 |

### 2.3 差异化（对标现有开源方案，诚实版）

| 竞品 | 定位 | AKB 的差异化主张 |
|---|---|---|
| Unstructured / Docling / MinerU | 单点文档解析，做得比 AKB 深、快、稳 | AKB 不和它们比解析精度，比"解析后知识怎么被管理" |
| 纯向量 RAG（LangChain 模板类项目） | 查完就走，不沉淀 | AKB 加了"该不该沉淀"的判断层（Router） |
| Karpathy 的 LLM-Wiki | 纯编译，个人用、100-200篇上限 | AKB 用 Router 做冷热分层，试图突破这个规模上限 |

**诚实提醒**：这个差异化目前只在架构设计层面成立，Compile层没有LLM参与、Router的冷热判断是启发式规则而非统计学习，都还没有真正验证"能解决规模问题"。

## 三、目标架构

### 3.1 完整架构图（目标状态，非当前状态）

```
                         用户提问 / 新文档
                                │
                    ┌───────────┴───────────┐
                    │      Orchestrator      │  总控：识别、规划、调度
                    └───────────┬───────────┘
           ┌────────────────────┼────────────────────┐
           │                    │                    │
      [摄取路径]            [质检路径]            [查询路径]
           │                    │                    │
    ┌──────┴──────┐      ┌──────┴──────┐      ┌──────┴──────┐
    │ Ingest Agent │ ───▶ │Quality Agent│      │Router: query │
    │ PDF/网页/文本 │      │乱码/空块/OCR │      │Wiki优先RAG兜底│
    └──────────────┘      └──────┬──────┘      └──────┬──────┘
                                  │                     │
                          ┌───────┴───────┐    ┌────────┴────────┐
                          │Router:classify │    │                 │
                          │  冷热分层判断   │    ▼                 ▼
                          └───┬───────┬───┘  Compile层(Wiki)   RAG层(向量库)
                              │       │      结构化沉淀        实时检索
                         hot  │       │ 总是
                              ▼       ▼
                        Compile Agent  Index Agent
                        (LLM真编译)     (向量+关键词索引)
                              │
                              ▼
                        Wiki: entities/concepts/synthesis
                        + 实体抽取 + 双向链接 + 矛盾检测
                              │
                              └──────────┐
                                         ▼
                                   Memory 层
                              (会话状态/追问上下文/
                               用户偏好/历史交互)
                                         │
                                         ▼
                                  Answer Agent
                              (LLM生成 + 带引用 + 置信度)
```

### 3.2 与当前状态的差距清单

| 架构组件 | 目标状态 | 当前状态（若保留今日新增） | 差距 |
|---|---|---|---|
| Orchestrator | 调度全部6个Agent，含human-in-the-loop | 调度4个Agent的摄取链路，查询链路走Router | 缺质检失败的人工介入、缺LangGraph图编排（现在是硬编码调用顺序） |
| Ingest | PDF+文本+网页+图片+代码仓库 | PDF+文本+网页，**无图片OCR** | 图片/代码仓库摄取器未写 |
| Quality | 机械检测+语义检测（矛盾/过时） | 仅机械检测（乱码率/空块/扫描件） | 语义检测需LLM，未做 |
| Router | 启发式规则+统计回流（高频内容自动升级为hot） | 仅启发式规则 | 回流机制未做，是长期缺口 |
| Index | 向量+关键词混合检索 | 仅BM25关键词 | 无embedding，语义查询能力缺失 |
| Compile | LLM抽取实体概念、生成双向链接、矛盾检测 | 纯格式转换，entities/concepts目录常年为空 | **这是最大的名不副实点** |
| Answer | LLM生成+置信度+溯源 | 仅拼接召回片段，不调LLM | 本质是检索展示，非问答 |
| Memory | 会话状态+追问+用户偏好 | 完全不存在 | 从零开始 |

## 四、开发方案（分阶段，标注前置依赖）

### 阶段划分原则

不是"一次性做完所有差距"，是按**"这一步做完能不能独立验证价值"**排序：

```
M0 已完成：数据契约 + 识别器 + 摄取保真（PDF/文本/网页）
M1 已完成：RAG检索 + 问答闭环（检索式，非生成式）
M2 已完成：Compile骨架（归档式，非编译式）
─────────────────────────────────────────────
M3 待定：Orchestrator + Quality + Router 打通冷热分层  ← 今日已写代码，未提交/未确认
M4 待做：Compile 真编译（接LLM）—— 硬依赖：LLM API key 或本地 Ollama
M5 待做：Answer 真生成（接LLM）—— 同上依赖
M6 待做：向量检索（embedding + 混合检索）
M7 待做：Memory层骨架（会话状态，不依赖LLM可先做）
M8 待做：Router回流机制（高频内容统计升级为hot）—— 依赖M3+M6跑一段时间产生数据
M9 待做：图片OCR摄取器
M10 待做：文档/README/PRD 与代码状态重新对齐
```

### 关键阻塞点（必须先决策）

1. **M4、M5 都硬依赖 LLM 接入**——这是当前最大阻塞。选项：
   - DeepSeek/OpenAI API key（成本低，需联网，数据出本机）
   - 本地 Ollama（免费，数据不出本机，需要本机算力，模型能力弱于云端）
2. **M3 的去留**——今日已写但未提交的三个文件，决定后续所有阶段的代码基线。
